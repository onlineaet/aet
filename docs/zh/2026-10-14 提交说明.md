## 一、设计背景

在将 llm.c 移植到 AET 的过程中，需要处理 CUDA 平台特有的内存访问指令。

例如，在 `layernorm_forward_kernel3` 中，有一行代码：

```
__ldcs(x + c);
```

其中，`__ldcs` 来自 CUDA 提供的 `sm_32_intrinsics.hpp`，其实现类似于：

```
__SM_32_INTRINSICS_DECL__
long __ldcs(const long *ptr)
{
    unsigned long ret;
    asm volatile (
        "ld.global.cs.s64 %0, [%1];"
        : "=l"(ret)
        : __LDG_PTR (ptr)
    );
    return (long)ret;
}
```

该函数通过内联汇编生成 CUDA PTX 指令 `ld.global.cs.s64`，执行带有 `.cs` 缓存策略的全局内存加载。

直接调用 `__ldcs` 可以解决 CUDA 平台上的问题，但用户代码必须引入 CUDA 提供的相应 intrinsic 头文件，才能获得函数声明及其实现。这会使上层代码依赖特定平台的接口，也不利于同一份代码面向多个目标平台。

MTCS 的目标是支持多个计算平台，包括 CUDA、GCN 等。如果平台无关代码直接引用 CUDA 的 intrinsic 接口，那么在切换到其他平台时，就需要调整代码中的接口引用，甚至修改调用逻辑。

因此，AET 引入了新的 Intrinsic 函数机制：**将平台无关的接口声明与平台相关的具体实现分离，由编译器根据当前目标平台查找并关联相应实现。**

用户只需调用统一的接口，不必直接引用平台提供的 intrinsic 头文件，也不必了解具体实现类中的汇编代码。

## 二、Intrinsic 机制设计

AET 原有的函数处理体系包括三种类型：

1. 普通函数。
2. 内建函数（builtin）。
3. 内部函数（internal-fn）。

本次新增第四种函数类型：Intrinsic。

Intrinsic 机制通过类属性区分平台无关的接口类和平台相关的实现类，使编译器能够在生成具体目标平台的代码时，查找并关联对应的实现。

### 2.1 平台相关实现：mii

`mii` 是 **MTCS Intrinsic Implement** 的缩写，用于标识平台相关的 Intrinsic 实现类。

例如，CUDA 平台可以提供如下实现：

```
public$ final$
__attribute__((mii("cuda", "sm_35")))
class$ CudaMemInstrinsic
{
public$ static __device__
float ldcs(const float *ptr)
{
    float ret = 5;
    asm volatile (
        "ld.global.cs.f32 %0, [%1];"
        : "=r"(ret)
        : "R"(ptr)
    );
    return ret;
}
};
```

`mii("cuda", "sm_35")` 用于标识实现所对应的平台和架构。具体实现封装在类的静态方法中，并定义在编译器可见的头文件中。

其他目标平台也可以提供各自的实现。平台相关的汇编和实现细节保留在相应的实现类中，而不暴露给用户代码。

### 2.2 平台无关接口：mic

`mic` 是 **MTCS Intrinsic Class** 的缩写，用于标识平台无关的 Intrinsic 接口类。

例如：

```
public$ __attribute__((mic()))
class$ Target
{
#pragma mtcs intrinsic
    public$ static __device__
    float ldcs(const float *ptr);
};
```

这里的 `Target` 只是示例中的接口类名称，并非机制要求的固定名称。

该类只声明统一的调用接口，不提供具体实现。`#pragma mtcs intrinsic` 用于标识相应的 Intrinsic 声明。

用户代码调用该接口时，不需要直接引用 `CudaMemInstrinsic`，也不需要知道具体的平台实现类。

### 2.3 编译器如何关联接口与实现

Intrinsic 机制涉及三个部分：

- **用户代码**：调用平台无关的 Intrinsic 接口。
- **平台无关接口类（mic）**：声明统一的静态方法，不提供具体实现。
- **平台相关实现类（mii）**：通过平台和架构属性标识目标，并提供相应的静态方法实现。

编译器根据当前编译目标，查找与平台无关接口相匹配的平台实现，并将调用关联到相应实现。

```
用户代码
    |
    v
平台无关接口类（mic）
    |
    v
AET 编译器
    |
    +---- 查找 CUDA 实现（mii）
    |
    +---- 查找 GCN 实现（mii）
    |
    +---- 查找其他目标平台的实现（mii）
    |
    v
生成当前目标平台的代码
```

上图表示逻辑关系，并不意味着编译器必须依次查找所有平台。实际实现由当前编译目标决定。

通过这种机制，平台无关代码不再直接依赖某个目标平台的 intrinsic 头文件。平台相关的实现由编译器查找和关联，用户只需要使用统一的调用接口。

## 三、设计目标

该机制主要解决以下问题：

1. **平台解耦**：避免用户代码直接依赖 CUDA、GCN 等平台专用的 intrinsic 接口及其头文件。
2. **统一调用**：通过平台无关接口，为不同目标平台提供统一的调用形式。
3. **编译器负责关联**：依据当前编译目标查找并关联具体实现，避免用户代码自行选择平台实现类。
4. **实现细节透明**：平台相关的汇编和实现细节封装在实现类中，对使用统一接口的用户代码不可见。
5. **便于扩展**：增加目标平台时，可以提供相应的实现类，而不必修改平台无关的调用代码。

该机制并不消除不同硬件平台之间的差异，而是将这些差异封装在平台实现层，由编译器负责连接统一接口与具体实现。

这也是 AET 面向多平台编译的一个重要方向：**编写一次，多芯运行。**
